# UI profile: 구현과 검토가 가능한 화면 설계

## 먼저 고정할 입력

정확한 UnitSpec 입력 pins, 승인된 시스템 범위, 사용자/역할·주요 과업, 기존 디자인 시스템/소스, 화면에 연결될 API·데이터 계약을 확인한다. 산출물 방식은 Gate A의 tool_plan과 실제 사용자 요구를 따른다. UI 기본은 preferred: Figma를 먼저 시도하고 실제 차단이면 Gate A에서 승인한 로컬 배치안으로 대체한다. required는 편집 가능한 native 결과가 완료 조건이며 자동 fallback하지 않는다. local_only는 실제 사용자의 명시 선택이 있을 때만 사용한다. UI 단위는 browser required 계획도 함께 있어야 한다.

## 반드시 구체화할 내용

| 항목 | 결정할 내용과 검토 자료 |
|---|---|
| 화면 목록/흐름 | 화면 ID·목적·진입/종료·역할·경로·전후 화면, 주요 과업의 순서 |
| 배치 | 영역별 우선순위·크기/정렬·여백·스크롤·고정 영역·작은 화면에서의 재배치 |
| 구성요소 | 기존 component ID/코드 대응·variant·입력/출력·상태·재사용/신규 이유 |
| 시각 토큰 | 색상 역할과 실제 값/token, 글꼴·크기·행간·간격·반경·경계·그림자 |
| 반응형 | 기준 viewport와 변형 규칙, 최소 폭·가로 넘침·긴 문구·다국어·확대 처리 |
| 조작 | 클릭/터치/키보드·단축키·선택·확인/취소·중복 입력·연속 입력의 의미 |
| 접근성 | semantic 역할·label·읽기 순서·탭 순서·focus 이동/복귀·오류 안내·실시간 알림 |
| 데이터 | 표시 필드·출처·단위·정밀도·포맷·정렬·필터·pagination·시간대·갱신 정책 |
| 상태 | 초기/로딩/빈 결과/정상/유효성 오류/통신 실패/권한 없음/부분 결과/복구 |
| 연결 계약 | UI 이벤트→상태 전이→요청/응답→사용자 피드백, race/stale 응답·취소 정책 |

제품에 없는 상태를 억지로 추가하지 말고 해당 없음과 이유를 적는다. “깔끔하게”, “적절한 색상”으로 실제 선택을 대신하지 않는다. 기존 토큰이 있으면 우선 사용하고 임의 하드코딩을 늘리지 않는다. 상태의 단일 출처와 비활성/읽기전용/오류 차이를 명확히 한다.

## Figma 작업 절차

1. 실제 사용 가능한 도구·파일 권한·현재 파일/노드를 확인한다. 기존 library/component/variables를 필요한 범위로 조회한다. 프로젝트 전체 파일 dump 대신 화면과 관련된 구조부터 읽는다.
2. 호스트에 설치된 Figma 전문 Skill 중 현재 동작에 해당하는 지침을 읽는다. 새 파일·도식·전체 화면·component·코드 변환은 도구별 선행 조건이 다를 수 있다. Skill이 없으면 실제 도구 schema/공식 문서를 읽고 미확인 기능을 추측하지 않는다.
3. 사용자에게 허용된 대상에서 native frame/component/variant/auto-layout/variables를 사용해 필요한 화면과 상태를 작성한다. 단순 빈 파일 생성이나 screenshot 업로드로 화면 설계 완료라 하지 않는다.
4. API 계약과 맞는 fixture 표시 데이터를 쓴다. 실제 개인정보·운영 원문·비밀을 디자인에 복사하지 않는다. mock은 실제 연동 결과가 아니라고 표시한다.
5. 구조를 다시 읽어 편집 가능한 node·component·variant와 연결을 확인한다. screenshot으로 배치·잘림·겹침·대비·주요 상태 누락을 검토한다. 핵심 과업과 키보드/focus 설계도 문서에 대조한다.
6. 실제 반환된 file/node refs·사용한 도구·내부 call ref·관찰 시각·필요한 구조/이미지 증거를 보존한다. 공급자가 안 준 remote revision/ETag는 만들지 않는다.
7. 승인 묶음은 그 시점의 정확한 unit 계약과 디자인 관찰을 고정한다. 외부 Figma가 계속 바뀔 수 있으므로 구현 직전에 관련 영역을 재확인한다.

편집 도구가 노출되지 않거나 대상 권한·쿼터가 막혔으면 이유와 독립적으로 만든 로컬 설계 자료를 제시한다. Figma 필수 요구를 자동으로 문서/이미지 방식으로 낮추지 않는다. preferred 대체에는 실제 실패 도구·원인·관찰 시각과 승인한 로컬 결과를 tool_observations에 기록한다. local_only는 사용자의 실제 선택 출처를 기록하며 AI가 선택 문구를 만들지 않는다. native link와 저장 이미지는 외부 상태 복원 보장이 아니다.

## 문서/로컬 배치안

문서 방식은 페이지/상태별 SVG 또는 정적인 HTML 배치안과 화면 계약 MD를 제공할 수 있다. 색·여백·실제 문구·버튼 위치·상태 예시가 검토 가능해야 한다. 프로토타입은 제품 구현·실행 테스트와 구분하고 제품 폴더를 미승인 상태로 수정하지 않는다.

## 완료 점검과 테스트 인계

요구/case ID→화면/상태/component→사용자 이벤트/예상 결과를 연결한다. 각 interaction의 결과를 테스트 설계가 독립적으로 판정할 수 있어야 한다. 시각 비교 대상 viewport·reference 관찰, focus/키보드·오류 복구·긴 값/빈 값 등 경계 사례를 전달한다. 실제 Figma 파일·노드와 로컬 자료는 사용자가 바로 열 수 있는 링크로 제공한다.
