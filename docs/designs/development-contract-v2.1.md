# 개발 환경 인증·DB 정량 작업·변경 범위의 최종 보완 설계

설계 판: D2 / 작성일: 2026-09-21 / 목표 구현 버전: 2.1.0

**상태: 사용자의 구현 요청에 따라 2.1.0에 적용한 기준 설계다. 실제 기능과 제한은 [2.1 실행 계약](../v2.1-operations.md)을 확인한다. SQL Server adapter는 검증 가능한 typed 작업부터 지원하며, 실제 DB 연결·변경 검증과 AI 계정 인증은 각 사용자 환경에서 별도로 확인해야 한다. 설계 문서 자체는 시험 성공 증거가 아니다.**

팀원 초기 설치의 진입점은 [START-HERE.md](../../START-HERE.md)다. 스타터는 받은 원본의 실제 기능을 확인하여 설치하고, 미구현 기능을 완료로 표시하지 않는다.

## 1. 반드시 충족할 사용자 요구

| ID | 요구 | 설계상 완료 조건 |
|---|---|---|
| ENV-01 | 사용자가 `.env`로 개발 환경의 인증·연결 값을 관리 | 개인 profile별 `.env`, 역할별 주입, 값 없는 보고, 변경 감지, 기존 설정 보존이 실행 경로에 연결 |
| DB-01 | DB 개발도 정량적으로 계획·진행·검증 | 객체·데이터·migration·실행 한도와 계획/실제 차이를 구조화하고 실제 결과로 완료 판단 |
| SCOPE-01 | 사용자가 백엔드·화면 파일 및 DB 변경 범위를 알고 승인한 뒤 개발 | 필수 변경 목록을 사람이 읽는 표로 제시하고 동일 manifest를 Gate B와 실행에 고정 |
| BOOT-01 | 팀원이 Git으로 받은 뒤 AI가 초기 환경 설정을 주도 | 설치 전 Skill이 없어도 실행할 수 있는 스타터, 실제 설치 명령, 호스트 진단, 개인 완료 보고, 재개 절차 제공 |

이 네 항목은 지침 문구만 추가하는 것으로 완료하지 않는다. Skill의 산출물, Harness의 schema·검증·실행, 설치기, 회귀 시험까지 연결한다. 아래 내용은 구현 기준이며 실제 배포 기능의 제한을 숨기지 않는다.

## 2. 설계 당시 2.0 기준과 보완 이유

아래 목록은 설계 당시 2.0.0 공통 실행기와 11개 Skill에서 확인한 차이다. 2.1의 현재 동작은 이 차이를 보강한 것으로, [실행 계약과 지원 제한](../v2.1-operations.md)을 확인한다.

- [개발 길잡이](../../skills/development-workflow/SKILL.md)는 정확한 산출물 refs, 두 Gate, 개별 단계 재호출을 이미 설명한다.
- [단위 설계](../../skills/dev-unit-design/SKILL.md)는 화면·API·데이터·통합 profile을 조합할 수 있다. 새 화면/DB 설계 Skill을 중복 추가할 필요는 없다.
- [workflow.py](../../harness/workflow.py)의 unit-spec 필수값은 요구·case ID 중심이다. 파일별 변경 action과 DB 작업 수치가 필수 schema는 아니다.
- 2.0 [execution.py](../../harness/execution.py)의 `allowed_paths` 검사는 종료 후 수행됐고, 목록이 없거나 비어 있으면 해당 범위 검사가 적용되지 않았다. 2.1은 필수 scope와 사전·사후 검사를 적용한다.
- 같은 실행기의 상속 환경 필터는 비밀처럼 보이는 이름을 제외하지만, 모든 인증 키를 식별하지 않는다. 개인 `.env`를 역할별 프로세스에 주입하는 공통 resolver도 없다.
- 실제 DB target·schema·fixture·객체 수·영향 행수와 서버 준비/정리를 검사 결과에 묶는 계약이 없다.
- 2.0 [install.py](../../install.py)는 실제 `.env`/키 파일 차단, 고정 release·백업·두 호스트 파일을 제공했으나 Skill 수를 11개로 고정했다. 2.1은 release 선언과 명시적 패키지 파일 목록을 사용한다.
- [doctor.py](../../scripts/doctor.py)는 CLI/MCP와 선택한 Codex 검색을 확인한다. Claude native 확인과 외부 서비스 계정 연결 성공까지 대신하지 않는다.

정확한 승인 기록과 소스 snapshot 기반은 유지한다. 아래 세 계약을 필수 구조로 보강하고, 설치기에는 starter와 기능 목록을 연결한다.

## 3. 사용자에게 먼저 보여줄 변경 범위

### 3.1 시스템 설계와 단위 설계의 역할

Gate A에서 사용자는 기능 범위, 영향 계층, 대상 시스템/DB, 작업 단위와 예상 규모를 본다. 기존 프로젝트에서는 실제 조사한 모듈/파일을, 신규 프로젝트에서는 제안 구조와 파일 배치안을 제시한다.

Gate B에서는 **이번 구현에서 생성·수정·삭제할 파일과 DB 객체**를 실제 상대 경로 및 이름으로 확정한다. 파일 목록이 미정인 일반 구현을 전체 폴더 권한으로 바꿔 승인받지 않는다. 동적 생성물이 있다면 아래 생성 규칙을 별도로 적용한다.

사용자가 보내는 승인 문구는 제시된 review ID와 그 묶음에 고정된 scope ref를 가리킨다. 사용자가 hash를 직접 계산하거나 파일 목록을 손으로 작성하게 하지 않는다. AI가 조사·설계·표 작성을 수행하고, 사용자는 실제 내용을 확인한다.

### 3.2 필수 사용자 범위표

각 단위의 승인 자료에는 다음 표와 합계를 포함한다. 다음 행은 형식을 설명하는 **예시**이며 특정 프로젝트의 승인 범위가 아니다.

| 계층 | 정확한 변경 대상 | 작업 | 이유/사용자에게 생기는 동작 | 요구·검사 |
|---|---|---|---|---|
| 화면 | `src/pages/DocumentPage.tsx` | 생성 | 문서별 화면 표시 | 요구 ID / case ID |
| 화면 | `src/components/NoteList.tsx` | 생성 | 메모 목록·저장 상태 표시 | 요구 ID / case ID |
| 백엔드 | `server/routes/notes.ts` | 생성 | 메모 검증·저장·조회 API | 요구 ID / case ID |
| DB 실행 파일 | `db/migrations/001_notes.sql` | 생성 | 검토된 DB 변경을 재현 | DB 작업 ID |
| DB 객체 | `<target>.<schema>.Notes` | 테이블 생성 | 문서와 메모의 관계·저장 | DB 작업 ID / case ID |
| 시험 | `tests/notes.integration.test.ts` | 생성 | 실제 DB 저장 확인 | case ID |
| 설정/의존성 | `package.json`, 실제 lockfile | 수정 | 승인한 실행/시험 의존성 | 변경 이유 / 검사 |

프레임워크는 이 예시로 고정하지 않는다. 실제 프로젝트가 .NET, Python 등이라면 조사한 관례와 실제 경로를 사용한다. 아래 합계는 schema에서 계산해 표와 함께 보여준다.

- 계층별 생성/수정/삭제 파일 수, rename 수, 필수 파일 수.
- DB 종류별 생성/변경/삭제 객체 수와 migration 수.
- 영향을 받는 API·화면·DB 의존 객체와 데이터 변경 범위.
- 새 의존성·개인 환경 설정 변경, 이전 호환성·데이터 보존 영향.
- 미확정 항목, 실행을 막는 항목, 명시적으로 제외한 범위.

`backend/**`, `src/**`, “DB 일부”처럼 대상이 드러나지 않는 목록만으로 일반 구현 Gate B를 완료하지 않는다. 불필요하게 전체 저장소 파일을 나열하지 않고 이번에 변경할 대상과 읽기 영향 범위를 구분한다.

### 3.3 `scope-manifest` 제안 계약

아래 필드는 신규 설계다. 현재 operation에 지원되는 필드인 것처럼 전송하면 안 된다.

| 부분 | 필수 내용 |
|---|---|
| 식별 | project/workspace/run/unit, 요구 refs, 기준 source snapshot, scope revision; hash는 저장 후 반환되는 ref에 포함 |
| 일반 파일 | layer, normalized relative path, create/modify/delete, reason, requirement/case IDs, required 여부 |
| 파일 기준 | 생성은 `expected_absent`, 수정·삭제는 변경 전 SHA-256; 다른 원본으로 조용히 대체 금지 |
| rename | 원본 경로 삭제 + 목적 경로 생성의 연결 관계; 수정된 내용 여부 별도 |
| DB 범위 | 승인한 target ref, schema, object type/name, create/alter/drop/data-change, DB 작업 ID와 baseline |
| 생성물 | 승인 generator와 버전·입력 hash, output root·제한 패턴·action·최대 파일 수·바이트 한도 |
| 실행 임시물 | cache/log/coverage/trace 등의 별도 scratch/evidence root·종류·수명·한도 |
| 개인 설정 | host/profile의 변경 항목 이름과 적용 receipt; secret 원문 없음 |
| 선행 근거 | 요구·단위·환경/DB 계획의 정확한 refs; 뒤에 생성될 review ID는 scope 본문에 넣지 않음 |

승인 연결은 scope와 별도의 불변 기록으로 둔다. 그 기록이 review ID, 제시된 문서/표 ref, 저장된 scope ref/hash, 관련 계획 refs를 묶는다. scope가 자신을 승인한 review나 자기 hash를 본문에 역참조하지 않으므로 순환이 생기지 않는다.

실제 경로는 제품 root 기준 상대 경로로 고정한다. 절대 경로 탈출, `..`, 링크/reparse, 다른 제품이나 공통 원본 경로를 허용하지 않는다. 서로 겹치는 unit의 파일 소유권과 선행 관계를 확인한다.

생성기가 사전 preview로 파일 목록을 낼 수 있으면 그 실제 목록을 승인 자료에 넣는다. 미리 정할 수 없는 파일명은 사용자가 이해할 수 있는 bounded 생성 규칙을 명시하고, 실행 후 실제 목록을 고정한다. 생성 규칙은 일반 소스 수정 권한을 대신하지 않는다. 전체 제품 root에 무제한 생성/수정을 허용하는 규칙은 거부한다.

### 3.4 실행 전·후 확인과 범위 변경

1. `begin_implementation`은 유효 Gate B, 비어 있지 않은 scope, 해당 단위에 필요한 환경/DB 계약, 기준 파일 상태를 확인한다. DB를 사용하지 않는 단위는 근거 있는 N/A를 허용한다. 일반 구현에 범위 목록이 없으면 시작을 거부한다. 변경 없음 재관찰은 별도 명시적 mode로 처리한다.
2. Harness가 직접 수행하는 쓰기·생성·DB 준비는 실행 직전에 해당 action과 대상을 검사한다. AI도 각 편집 묶음 전에 계획된 경로와 action을 확인한다.
3. 종료 시 실제 A/M/D 파일과 DB 객체·데이터 결과를 승인 manifest와 대조한다. 필요한 파일의 누락, 허용하지 않은 파일, action 불일치, baseline 변경을 별도 상태로 기록한다.
4. 범위 밖 변경이 필요하면 AI가 이유·새 경로/객체·수량·영향·검사를 제시하고 새 scope/test-plan revision을 만든다. 영향받는 Gate B를 검토하기 전에 그 변경을 실행하지 않는다.
5. 승인된 파일 안에서 계약과 범위를 유지하는 버그 수정은 불필요하게 새 범위 승인을 요구하지 않는다. 새 파일/객체·삭제·의존성·공개 계약 변경이면 범위를 다시 판단한다.

같은 OS 계정의 외부 편집기나 AI의 native 편집 도구 전체를 Harness가 가로채는 구조는 아니다. 이 경로의 사전 차단을 보장하지 않으며, Skill의 편집 전 확인과 이후 실제 diff 검증을 결합한다. 범위 밖 변경을 감지하면 완료와 후속 쓰기를 차단하고 증거를 보존한다. 사용자의 변경을 자동 삭제하거나 Git reset으로 되돌리지 않는다. 강제적인 파일 접근 격리가 필요하면 향후 별도 OS sandbox 또는 모든 쓰기를 통과시키는 실행 구조가 필요하다.

## 4. `.env`를 통한 개인 개발 환경 인증

### 4.1 구조와 사용자 경험

개인 root 아래에 프로젝트/용도별 profile을 둔다. 한 사용자에게 여러 개발·시험 환경이 있을 수 있으며, 모든 프로젝트가 하나의 전역 비밀 묶음을 공유하지 않는다.

```text
<personal-state>/environments/<profile-id>/
  profile.json          # 대상·역할·설정 key 매핑; 원문 secret 없음
  secrets/.env          # 사용자가 편집하는 실제 연결·인증 값
  secret-state.json     # 개인 전용 변경 감지 자료
```

신규 `dev-environment`가 필요한 키를 조사하고 값 없는 파일과 입력 안내를 작성한다. 실제 값 입력 후 사용자에게는 필수 값의 있음/없음, 형식, target, 역할별 연결·권한 상태만 보여준다. 비밀 값 자체를 읽어달라고 요청하거나 채팅으로 전송하게 하지 않는다.

공통 Git에는 `.env.example`, schema, key 설명만 둔다. 개인 `.env`, profile의 실제 서버 정보, 호스트 자격증명과 백업은 공통 패키지·개인 소스 journal·일반 산출물 export에서 제외한다. 사용자별 파일 권한을 설정하고 재점검한다.

### 4.2 인증 방식과 역할

| 인증 대상 | 관리 방식 |
|---|---|
| DB/개발 API의 직접 연결 값 | 개인 `.env` + profile의 허용 key/역할 매핑 |
| SQL Server 통합 인증 | 선택한 OS 인증 문맥과 대상/권한을 관찰; 불필요한 암호 키 요구 금지 |
| OAuth 기반 외부 서비스 | 각 호스트/서비스의 정상 인증 저장소 사용; 토큰을 `.env`로 강제 추출하지 않음 |
| Codex/Claude/GitHub 사용자 로그인 | 해당 제품의 공식 로그인 절차. 다른 팀원의 토큰이나 계정 복사 금지 |

개발 환경 연결용 인증과 개발할 앱의 최종 사용자 로그인 기능은 별개다. `.env`를 구성했다고 앱 사용자 인증·인가가 구현된 것은 아니다.

DB 역할은 inspect, application, migration/fixture로 분리한다. 브라우저는 API를 호출하고 DB 비밀을 받지 않는다. 앱 서버에 migration 권한을 기본 주입하지 않는다. 공급자의 광범위한 전체 DB 역할보다 승인한 schema/object의 최소 권한을 우선한다.

### 4.3 실행 계약

- AI와 MCP 요청은 profile ID·revision·역할만 전달한다. 원문 secret을 argv, JSON/TOML 설정, 설계 문서에 복사하지 않는다.
- Harness의 내부 resolver가 개인 파일을 읽고 schema를 검사하여 승인된 프로세스에 필요한 키만 주입한다. 환경 원문을 반환하는 공개 도구는 만들지 않는다.
- OS 실행에 필요한 기본 변수와 명시적 허용 키만 상속한다. 변수 이름 제외 목록만으로 secret을 판단하지 않는다.
- `.env`는 셸로 실행하지 않는다. 변수 확장·명령 치환·암묵적 다른 프로젝트 검색을 금지하고 중복·미등록 키·타입 오류를 처리한다.
- 우선순위는 profile의 실행 계약으로 명시한다. 기존 앱 로더가 다른 `.env`로 다시 덮어쓰는 경우를 검사한다.
- 공개 프런트엔드 변수에 secret을 매핑하면 거부한다. 알려진 주입 값과 연결 문자열을 출력에서 마스킹하고 로그/증거 파일 정책을 적용한다.
- 실행 시 관찰한 실제 DB target·schema·권한과 승인된 범위를 비교한다. 다른 대상이면 쓰기 전에 차단한다.
- 비밀 변경은 개인 keyed HMAC 등으로 감지하고 원장에는 opaque revision만 남긴다. 원문 secret의 평문 hash를 게시하지 않는다.

암호만 교체되고 대상·권한이 같으면 설계 재승인을 요구하지 않는다. 다만 새 연결 확인과 관련 검증 결과 갱신은 필요하다. DB·schema·권한·외부 전송 범위가 바뀌면 해당 변경의 승인을 확인한다.

기존 프로젝트의 `.env`와 사용자 설정은 보존한다. 명시적으로 선택한 키만 로컬로 가져올 수 있게 설계하되, 원본 자동 삭제·일괄 이동·다른 환경의 값으로 조용히 덮어쓰는 방식은 사용하지 않는다.

## 5. DB 개발의 정량 계약

“정량적”이라는 것은 migration 파일 수를 세는 것만을 뜻하지 않는다. **무엇을 바꾸고, 어느 데이터에 얼마나 영향을 주며, 어떤 한도와 증거로 완료를 판단하는지**를 실행 가능한 계약으로 만든다.

### 5.1 `db-work-plan` 필수 항목

| 구분 | 계획에 고정할 값 |
|---|---|
| 작업 식별 | DB work ID, unit·requirement·case, target/environment ref, DB 엔진·확인한 버전 |
| 구조 변경 | schema·table·column·PK/FK/constraint·index·view·procedure·trigger·role/grant별 정확한 대상과 action |
| 변경 전 기준 | 실제 schema 관찰 ref·시각·정의 hash 또는 부재, 선행/의존 객체와 영향 |
| migration | ID·순서·내용 checksum·generator/입력/버전·예상 schema diff·중복 적용 정책 |
| 데이터 범위 | 테이블·검증 가능한 predicate·fixture namespace·대상 key, 예상 행수와 강제 최대 행수 |
| 보존 조건 | 기존 데이터 유지, 관계 무결성, 금지된 데이터/객체, 별도 백업 필요 여부 |
| 실행 한도 | statement/전체 timeout, lock 대기 한도, batch 크기, 재시도 조건·횟수, 중단/재개 조건 |
| 성능 검증 | 적용 시 fixture 규모·동시성·지표·허용값·측정 방법·환경; 불필요하면 이유와 N/A |
| 복구 | transaction 적용 가능 범위, 실패 시 rollback, 비가역 부분, 보상/복구 검증 계획 |
| 검증 | 사전/사후 관찰·데이터 검증 case·독립 oracle·증거·fixture 정리 조건 |

성능 기준을 모든 작은 CRUD에 대규모 부하 시험으로 강제하지 않는다. 구조/변경 수량, 영향 데이터, 안전 한도, 기능 검증은 필수이고 부하 지표는 제품 요구와 위험에 비례해 정한다. N/A는 이유를 기록한다.

실제 값이 아직 없으면 unknown과 해소 단계·책임을 기록한다. 미측정 예상치를 측정값처럼 채우지 않는다. 영향을 판단할 핵심 값이 unknown인 쓰기 작업은 실행할 수 없지만 독립적인 설계는 계속할 수 있다. 실측 baseline을 얻는 읽기 조사에도 대상·쿼리 시간/행 한도를 둔다.

### 5.2 사용자가 보는 DB 범위표

| 작업 ID | DB/schema/객체 | 작업 | 계획 수량/최대 영향 | 확인할 결과 | 복구 |
|---|---|---|---|---|---|
| 예시: db-001 | 승인 대상의 `Notes` | 테이블 생성 | 테이블 1개, 업무 행 변경 0 | 컬럼·키·제약이 설계와 일치 | 해당 DDL의 transaction 가능 여부 확인 |
| 예시: db-002 | 승인 대상의 특정 index | index 생성 | index 1개, 예상 데이터 규모 별도 | 정의·조회 계획/기능 기준 | 승인된 index 제거 또는 이전 정의 복원 |
| 예시: db-003 | 실행별 fixture 행 | 삽입/정리 | 생성 2행, 정리 최대 2행 | 해당 실행 ID의 행과 관계 | 해당 실행 소유 행만 정리 |

숫자와 객체명은 예시다. 그림판 테스트에 테이블 수·index 수·행수를 공통 상수로 박아 넣지 않는다. AI가 실제 설계와 조사로 표를 작성하고 사용자가 해당 표를 포함한 Gate B를 검토한다.

### 5.3 승인 전 SQL과 승인 후 실행

실행 예정 migration 내용은 Gate B 전에 **개인 설계 산출물**로 만들고 hash를 고정한다. 제품 파일이 아직 없으면 생성한 것으로 표현하지 않는다. 승인 후 같은 내용의 제품 파일을 만들고 대조한 뒤 실행한다.

코드로 migration SQL을 생성한다면 generator·버전·입력과 검토용 SQL을 연결한다. 생성 내용이나 대상이 달라지면 기존 승인으로 실행하지 않는다. 새 설계가 필요한 변경을 단순한 검사 재시도로 처리하지 않는다.

Harness의 DB adapter는 다음 순서를 제공해야 한다.

1. 실제 대상·권한·baseline·migration hash·연결 역할을 확인한다.
2. 적용 가능한 transaction과 동시 실행 잠금/소유권을 확보한다.
3. 사전 대상 행수·객체·의존성 및 실행 한도를 검사한다.
4. 승인된 변경을 실행하고 실제 객체 diff와 영향 key/행수를 얻는다.
5. commit 전에 확인할 수 있는 상한·불변식을 검사하고 위반하면 rollback한다.
6. commit 후 별도 새 연결로 내용·관계·schema를 확인하고 receipt를 보존한다.
7. 정리 대상이 실행 소유 범위인지 확인하고 정리 결과를 별도로 기록한다.

임의 SQL을 정규식으로 분석해서 모든 영향을 알아냈다고 주장하지 않는다. 검증 가능한 operation/adapter, DB 권한, transaction, 실제 catalog/data diff를 결합한다. 동적 SQL·암묵 commit·transaction 밖 변경 등 지원하는 방식으로 범위를 검증할 수 없는 작업은 별도 검토 대상으로 남긴다. 같은 DB의 외부 writer까지 차단한 것으로 표현하지 않는다.

“쿼리 성공”이나 rowcount 하나만으로 완료하지 않는다. 영향 행수는 지표의 일부이며 실제 key·값·문서 관계·인가·영속성 검사를 함께 수행한다. 테스트를 위해 운영 DB 서비스를 중단하거나 기존 업무 데이터를 지우지 않는다.

### 5.4 계획 대비 실제 보고

`db-execution-receipt`는 계획 ref·승인·환경/권한 관찰·migration hash와 함께 다음 값을 보존한다.

- 객체 종류별 계획/실제 create/alter/drop 수와 대상 목록.
- migration별 미실행/실행/이미 적용/실패/중단/복구 결과.
- DML별 대상 predicate/key, 예상/실제/최대 영향 행수.
- 실행·lock 대기·재시도 측정값, 적용한 timeout/batch 한도.
- 요구된 성능 검사의 데이터 규모·표본 수·지표·허용값·실측값.
- schema/관계/내용 검증, 기존 데이터 보존, fixture 정리 결과.
- 계획 대비 차이, rollback/보상 여부, 미확인 사항과 후속 차단.

초과·누락·지원 불가·불변식 위반은 완료 판정을 막는다. 이미 DB에 반영됐으나 후속 검사가 실패한 경우도 반영 사실과 실패를 분리해 기록하며 “아무 변경 없음”으로 표시하지 않는다. 소스 Git 복원과 DB 복구는 서로 다른 결과다.

## 6. Skill에 반영할 책임

신규 Skill은 `dev-environment` 하나로 총 12개를 제안한다. 추가 독립 DB 설계 Skill 대신 기존 단계와 데이터 reference를 강화한다.

| Skill | 필수 산출물/행동 |
|---|---|
| dev-environment | 개인 profile·빈 `.env`/키 안내·역할별 준비도·연결 관찰·적용 receipt |
| dev-discover | 실제 소스·환경·DB baseline·미확인 범위·기존 설정/권한을 조사 |
| dev-requirements | 결과 기준·문서/사용자 경계·정량 인수 기준·질문을 작성 |
| dev-system-design | 영향 계층·단위 의존성·예상 파일/DB 범위·검증과 복구 전략 |
| dev-unit-design | 필수 scope-manifest, 사용자 범위표, 정확한 UI/API/DB 계약, db-work-plan |
| dev-test-design | scope/DB 계획에 연결한 case·oracle·환경·fixture·수치 한도·증거 계획 |
| dev-review | 같은 refs로 만든 범위표·DB 수치·개인 환경 변경을 제시하고 실제 사용자 결정 기록 |
| dev-implement | 시작 전 기준/범위 확인, 승인한 파일·DB 변경 실행, 범위 확대 시 계획 재검토 |
| dev-verify | 실제 A/M/D·DB 계획 대비 실측·사례 결과·영속성·정리·완료 판정 |
| dev-artifacts | 사용자가 볼 범위표·계획/실제 DB 표·판별 변경·실패·현재성 조회 |
| dev-restore | 승인된 소스 복원과 DB 호환성/복구 차이를 명확히 제시 |
| development-workflow | 현재 근거와 허용 다음 행동으로 AI 작업을 이어가고 질의·승인·실패 복구를 조정 |

AI가 작성·실행을 주도하고, 사용자는 실제 범위와 중요한 결정을 확인한다. 범위표를 형식적으로 만들고 AI가 사용자 승인을 대신 생성하는 방식은 허용하지 않는다. 같은 OS 계정의 호출자가 제공하는 승인 기록이 신원 인증까지 제공하는 것은 아니므로 실제 대화 근거도 평가한다.

## 7. Harness와 설치기에 반영할 변경

| 부분 | 변경 |
|---|---|
| schema | environment-contract, scope-manifest, db-work-plan, service/fixture/evidence 계약을 추가하고 UnitSpec/TestPlan/Gate와 연결 |
| validation | 일반 구현의 빈 scope 거부, action/baseline/경로/수량/의존성/unknown 검사 |
| environment | profile resolver, key 허용 목록, 역할별 주입, secret revision·마스킹, 실제 target 확인 |
| execution | 구현 시작/종료 scope 대조, 준비 실행, DB adapter와 한도·실제 결과, 중단/정리 receipt |
| completion | 필수 단위·case·범위·DB 실측·환경·증거·정리가 모두 현재 유효할 때만 완료 |
| artifacts | 승인용 범위표와 계획/실제 표를 동일 schema로 생성, 개별 revision 조회·비교 |
| next_actions | 필요한 refs·질문·범위 변경·미결·허용 다음 단계 계산; 자동 승인 금지 |
| installer | 고정 Skill 수 대신 release manifest, 개인 비밀 제외, 기능 목록·호스트별 진단·구버전 유지 |
| starter | 실제 capability 확인, 설치·보고·재개, 계획뿐인 기능을 미지원으로 표시 |

새 schema를 저장하는 것과 실행기가 강제하는 것은 별개다. CLI와 MCP는 하나의 core와 operation 계약을 사용하고, 과거 버전이 임의 추가 필드를 무시한 채 새 기능처럼 동작하지 않도록 capability/version 검사를 둔다. 기존 run은 기존 release에 고정하고 새 계약의 완료로 변환하지 않는다.

회귀 시험에는 빈 `allowed_paths` 우회, 범위 밖 파일, 파일 action 불일치, 변경된 baseline, 다른 DB target, 과도한 DML 행수, 미선언 DDL 객체, 미등록 비밀 상속, unsupported migration, 증거/정리 실패, 사용자의 미커밋 변경 보존을 포함한다. 계정이 연결되지 않은 호스트를 전체 준비 완료로 표시해서도 안 된다.

## 8. 초기 스타터가 제공해야 하는 경험

팀원은 저장소를 clone한 뒤 Codex 또는 Claude Code에 **START-HERE.md를 읽고 초기 설정을 진행하라**고 요청한다. 초기 Skill 설치 전이므로 bootstrap 자체가 신규 Skill에 의존해서는 안 된다.

AI는 받은 원본·버전·README·실제 installer를 확인하고, 사용자 profile과 개인 state 위치를 식별한다. 기존 상태가 있으면 같은 경로와 설정을 재사용하고, 중요한 미정 사항만 질문한다. 원본·개인 state·제품 경로의 분리와 물리 경로를 확인한다.

구체적인 변경 계획을 보여준 다음 요청 범위의 설치를 계속한다. 정상적인 설치 단계마다 다시 승인을 묻지 않는다. 다른 사람의 자격증명, 제품 데이터, 팀 원격 설정을 복사하지 않는다. 사용하지 않을 클라이언트 설치·유료 모델 호출을 강제하지 않는다.

계정이 없어도 끝낼 수 있는 설치와 진단은 먼저 마치고, 사용자 로그인·값 입력이 필요한 단계만 후속으로 남긴다. 마지막에는 개인 설치 보고서와 receipt, 실제 연결/미연결, 기능별 준비도, 다음 호출문을 제공한다. 재실행하면 원장을 새로 만들거나 백업을 버리지 않고 기존 설정과 실패 위치에서 이어간다.

**현재 스타터는 2.1.0의 설치와 개인 환경 준비를 안내한다.** 실제 capability와 role probe를 확인하며, 이 설계 문서를 발견했다는 이유로 계정·DB 연결이나 미지원 작업을 준비 완료로 간주하지 않는다.

## 9. 구현 완료의 인수 기준

| 요구 | 꼭 통과해야 할 시험 |
|---|---|
| ENV-01 | 두 호스트가 같은 profile을 참조하고 역할별 변수만 받음; 원문 secret이 공통 Git·개인 journal·보고·argv·브라우저 결과물에 없음; 값 누락/교체/다른 target 정확 판정 |
| DB-01 | 승인된 객체·수량·행수로 실제 변경; 초과/미선언 변경은 지원 adapter에서 rollback 또는 명확한 실패; 독립 조회로 내용·관계·영속성 확인; 계획/실측/정리 표 제공 |
| SCOPE-01 | 사용자에게 제시한 manifest가 Gate B와 일치; 빈 scope·다른 baseline·새 파일/action·DB 객체 초과로 완료 불가; 범위 변화가 새 검토로 이어짐 |
| BOOT-01 | 새 clone과 가상 사용자 환경에서 실제 설치·CLI/MCP·호스트 검색 검증; 기존 설정 보존; 재실행·복원·계정 보류·구버전 기능 차이 처리 |

각 기능은 happy path뿐 아니라 실제 실패/차단과 재개를 검증한다. 임의 성공 JSON, 합성 사용자 승인, mock DB만으로 실전 개발 시험을 통과시키지 않는다. Harness 자체 회귀 fixture의 합성 결정은 실제 사용자 승인과 구분한다.

이 설계와 스타터 문서는 공통 원본에 보관할 수 있지만, 개인 경로·설치 결과·실제 연결 값·사용자 프로젝트 자료는 별도의 개인 영역에 둔다. 제품 예시는 이 계약의 시험 사례이며 표준의 고정 기능이나 고정 기술 스택이 아니다.
