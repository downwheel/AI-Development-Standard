# 2.1 실행 계약과 사용법

공통 core·12개 Skill을 설치해도 개인 DB 연결이나 AI 계정 로그인이 완료되는 것은 아니다. `info.capabilities`, 같은 release의 `describe`와 `contracts/artifact-payloads.json`, 실제 probe 결과를 함께 확인한다. 고정 release와 개인 기록 경로는 두 호스트에서 공유하며 제품 폴더에 기록용 Git을 만들지 않는다.

## 개인 환경

`dev-environment`는 프로젝트 등록 전에도 호출할 수 있다. `environment_plan`에 profile ID와 비밀 없는 typed profile을 전달하고, 반환된 계획을 `environment_apply`로 적용한다. 실행기는 개인 state의 `environments/<profile-id>/profile.json`, `secrets/.env`, private 변경 감지 자료를 만든다. `templates/environment/sqlserver.profile.json`과 같은 폴더의 키 안내를 사용한다. 기존 파일의 실제 값을 덮어쓰지 않는다.

사용자는 실제 `.env`를 로컬 편집기로 채운 뒤 `environment_inspect`와 각 역할의 `environment_probe`를 요청한다. 채팅에 비밀번호를 붙이지 않는다. SQL Server는 `inspect`, `application`, `migration` 계정을 구분하며 통합 인증도 가능하다. 프로필에는 값의 형식·필수 여부·역할별 목적지 키를 정의한다. 일반 개발 API는 `provider=process`로 같은 주입 계약을 사용할 수 있지만 이 provider의 probe는 외부 연결을 검증하지 않는다.

단위 환경 계약은 `profile_revision`, `target_revision`, `roles`, 실제 성공한 `probe_receipt_id`를 고정한다. 여러 역할은 공개 schema의 역할별 receipt 연결도 사용한다. 암호만 바뀌면 새 연결 확인과 재검사가 필요하고, 대상·계정 권한이 바뀌면 영향 계약을 다시 승인한다. OAuth와 Codex/Claude/GitHub 로그인은 각 서비스 저장소에 유지한다.

프로세스는 OS 실행에 필요한 허용 목록과 선택한 역할 값만 받는다. `.env` 확장·셸 실행·다른 프로젝트 자동 검색은 하지 않는다. 비밀을 명령 인자나 프런트엔드 공개 변수에 넣을 수 없다. 실제 값을 담은 자료는 공통 패키지와 소스 journal에 넣지 않는다. 같은 OS 계정의 다른 프로그램까지 격리하는 구조는 아니다.

## 개발 전 범위와 승인

1. 조사와 요구를 고정하고 시스템 설계에 `units`를 작성한다. 각 단위는 필수 여부, 선행 단위, requirement/case와 통합 검사 여부를 가진다. 누락·순환·알 수 없는 선행 단위를 거부한다.
2. 실제 사용자 Gate A 후 unit-spec을 작성한다. 환경과 DB가 불필요하면 각각 `required=false`와 이유를 기록한다.
3. 필요한 environment-contract와 db-work-plan, 이어 scope-manifest를 발행한다. scope는 unit과 앞선 계약을 참조하며 자기 hash나 미래 review ID를 포함하지 않는다.
4. scope의 파일에는 화면/백엔드/테스트/설정 계층, 정확한 상대 경로, create/modify/delete, 필수 여부, 이전 hash 또는 부재, 요구·case가 필요하다. rename은 delete+create로 표현한다. 생성물은 생성기·버전·입력 hash·하위 폴더·파일 형식·파일/바이트 상한을 고정한다.
5. 테스트 계획은 unit, scope와 필요한 계약 refs를 참조한다. `create_review`가 같은 scope에서 만든 표와 모든 문서의 presentation hash를 Gate B에 고정한다. 사용자가 이 파일·DB 표를 확인한 실제 응답을 기록한 뒤 구현한다.
6. `begin_implementation`에서 승인·범위·기준 소스·환경을 검사한다. AI는 편집 묶음 전 `check_edit_scope`로 경로와 작업을 확인한다. 종료 시 `finish_implementation`이 실제 diff와 필수 파일, DB 결과를 대조한다. native 편집기를 가로채는 기능은 아니므로 사전 확인과 사후 관찰을 함께 지킨다.

같은 승인 범위의 수정은 새 구현 세션으로 진행한다. 새 파일/DB 객체나 계약이 필요하면 새 revision과 해당 Gate B가 필요하다. 이미 적용한 같은 단위를 현재 소스에서 다시 검사할 때는 `mode=observe`로 변경 없는 새 receipt를 만들 수 있다. 그 세션에서 실제 편집하면 완료되지 않는다. 사용자 변경은 자동으로 지우지 않는다.

## SQL Server 정량 실행

필요한 선택 의존성은 Python의 **pyodbc**와 Microsoft **ODBC Driver 18 for SQL Server** 또는 호환되는 설치 드라이버다. profile의 TLS·timeout과 로컬 인증을 먼저 확인한다. 드라이버 설치만으로 DB가 연결된 것은 아니다.

`inspect_database`는 선택 프로필·역할로 정확한 테이블만 제한 관찰한다. 대상 fingerprint, 권한 fingerprint, 버전, schema·행수·내용 hash를 돌려주며 업무 행 원문을 반환하지 않는다. `preview_database`는 typed operation에서 실행 SQL과 파라미터 hash를 생성한다. AI는 이를 개인 설계 산출물로 보존해 승인에 고정한다.

`db-work-plan`에는 객체별 action/baseline, 순서와 SQL hash, 예상/최대 영향 행수, 정확한 key와 fixture 소유자, statement/transaction/lock/batch 한도, 보존·복구·oracle·정리 조건이 필요하다. `execute_database`는 현재 구현 세션의 승인된 계획만 실행한다. 대상·권한·baseline 검사, transaction·동시 실행 잠금, 실제 catalog/data 대조, 상한 검사 후 commit, 별도 새 연결의 관찰 및 정리 결과를 기록한다. 실패한 후속 검사와 이미 commit한 사실을 구분한다. 같은 request ID의 불확실한 DB 작업을 자동 재실행하지 않는다.

각 migration의 `source_path`는 scope에 필수 create/modify 파일로 선언한다. 승인 후 preview SQL을 정확한 UTF-8 bytes로 제품 파일에 만들며, DB 실행 직전에 그 파일의 hash를 다시 검사한다. 한 단위의 같은 DB target은 하나의 db-work-plan으로 묶고 여러 migration을 그 안에서 순서화한다. 다른 DB target은 별도 계획을 가질 수 있다. `get_database_execution`으로 원문 자격증명 없이 계획별 실행·중단 결과를 조회한다.

**현재 adapter 범위:** 테이블과 index 생성, 정확한 기본키로 제한한 insert/update/delete. 지원 자료형과 작업 schema는 `database.py`와 공개 계약이 권위다. 최대 관찰·배치 1,000행, catalog 5,000개, transaction 900초 이내에서 계획별 더 작은 한도를 적용한다. 자동 재시도는 0회다. 트리거·cascade·동적 SQL·임의 migration SQL·지원하지 않는 자료형/DDL·비 transaction 변경은 실행 지원으로 간주하지 않는다. 단순한 자체 성공 JSON으로 이를 우회하지 않는다. 복잡한 기존 운영 DB나 대용량 변경에는 별도 adapter 확장과 검증이 필요하다.

DB 복구는 소스 Git 복원과 별개다. 계획이 요구하는 실제 DB 백업과 복구 경로를 확인해야 한다. 정리 작업은 해당 실행 소유 fixture만 대상으로 하며 기존 업무 데이터 삭제를 허용하지 않는다. 실제 DB 검증이 없는 설치에서는 이 adapter의 합성 회귀 시험과 live DB 시험을 명확히 구분한다.

commit 여부가 불확실하면 해당 workspace의 새 DB 쓰기를 차단한다. 먼저 구현을 실패 상태로 종료하거나, 종료가 입증된 controller를 `reconcile_execution`으로 정리한다. DB adapter가 실행 중이면 구현 종료를 허용하지 않으며 lease 만료만으로 종료를 추정하지 않는다. `plan_database_recovery`는 원래 승인 대상과 객체를 읽기 전용으로 관찰하여 hash가 고정된 복구 검토 자료를 만든다. 사용자에게 이 자료를 보여 준 뒤 실제 응답을 `record_database_recovery`로 기록한다. 관찰 수락은 데이터 복원이나 SQL 재실행이 아니다. 해당 단위에 변경 요청을 등록하므로 새로운 기준의 설계·Gate B 승인 전에는 후속 쓰기를 진행할 수 없다. 검토 후 DB가 바뀌었거나 사용자가 거절하면 차단을 유지한다.

## 실행 준비·검사·증거

TestPlan의 check에는 선택적으로 `environment_ref`, `role`, `runner`를 둔다. `runner.kind=project-runner`의 상세 schema는 공개 계약을 조회한다. 제품의 Playwright/pytest 등 실제 검사 프로그램을 같은 소스에서 유지하고, 기대값을 구현과 독립적으로 작성한다.

- `services`: 승인한 executable/argv/cwd, 역할, 로컬 HTTP health URL, 준비 시간. 점유 포트를 재사용하지 않는다. Harness가 시작한 프로세스만 종료한다. health는 현재 `HARNESS_BUILD_ID`, `HARNESS_RUN_ID`를 JSON `build_id`, `run_id`로 응답해야 한다. Windows는 Job Object로 자식 프로세스를 관리한다.
- `fixture`: 제한된 setup/cleanup 명령, namespace와 실제 case 결과. 정리는 실패 시에도 시도하며 정리 실패는 완료를 막는다. 제품별 준비 로직은 승인한 프로젝트 runner에 둔다. 범용 raw SQL 권한을 대신하지 않는다.
- `evidence`: `HARNESS_EVIDENCE_DIR` 아래 정확한 text/json 상대 경로, 필수 여부, 최대 크기. 각 파일 최대 1 MiB, 최대 20개다. 원문 자격증명·브라우저 cookies/storage state는 첨부하지 않는다. 알려진 비밀 값을 제거한 파일과 content hash만 journal에 보존한다. PNG/ZIP/trace 바이너리는 이 자동 첨부 adapter에서 지원하지 않는다.

검사는 `HARNESS_CASE_RESULTS={"cases":[{"case_id":"...","status":"passed"}]}` 한 줄로 실제 사례 결과를 출력한다. 요구한 case의 누락·중복·skip은 통과가 아니다. build/lint 자체가 기준일 때만 명시적인 `command-exit`+`exit-code`를 사용한다. source/runtime/profile이 바뀌면 이전 pass를 현재 결과로 재사용하지 않는다. 실행 fingerprint는 파일 50,000개/512 MiB 한도이며 reparse/pnpm 링크 지원을 가정하지 않는다.

`next_actions`는 현재 자료·승인·실패에 맞는 다음 단계를 제시한다. `evaluate_completion`은 모든 필수 단위, 현재 검사, scope, DB 독립 관찰과 미해결 변경을 함께 확인한다. workspace 전체 snapshot을 사용하므로 다른 단위 개발 후 이전 단위를 `observe`하고 필수 검사를 다시 실행해야 할 수 있다. 자동 부분 결과 승계는 없다.

## 팀원 시작 요청

초기 설치는 [START-HERE.md](../START-HERE.md)의 요청문을 따른다. 설치 뒤 Codex에서는 `$dev-environment`, Claude Code에서는 `/dev-environment`로 개인 환경을 준비한다. 제품 개발은 `$development-workflow` 또는 `/development-workflow`에 제품 경로와 원하는 결과를 전달한다. AI가 조사·설계·테스트 계획·구현을 진행하고 사용자는 구체적인 두 설계 Gate를 검토한다.

계정이나 DB 값이 아직 없으면 독립적인 설계는 이어갈 수 있다. 연결 확인이 필요한 구현·검증을 성공으로 표시하거나 임의 환경으로 대체하지 않는다.
