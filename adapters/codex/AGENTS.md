## 팀 개발 스킬

- 이 환경의 개발 방법은 설치된 팀 개발 스킬을 사용한다. 사용자가 지정한 Skill과 작업 범위를 우선하며, 같은 결정이나 승인된 후속 작업을 반복해서 묻지 않는다. 기존 development-workflow/Gate/개인 원장 절차는 새 작업에 적용하지 않는다.
- Skill은 `$hi` 등의 영문 호출 이름 또는 선택 UI로 호출한다. 재사용 Skill은 Codex가 제공한 파일 경로에서 읽는다. Claude 전용 Skill 도구나 명령을 가정하지 않는다. 사용할 수 없는 병렬 도구는 순차 작업으로 대체한다.
- 출력과 프로젝트 연결은 `$CODEX_HOME/team-skills.json`(기본 `~/.codex/team-skills.json`)에서 확인한다. 프로젝트에 기존 Workspace 지정이 있으면 유지한다. 없으면 `workspace_root/<프로젝트명>-<정규화된 절대경로 SHA256 앞 8자>`를 프로젝트 Workspace로 사용하고 실제 경로를 보고한다.
- 제품 소스·빌드 설정·프로젝트 Harness는 제품 영역에 둔다. 신규 AI 테스트·fixture는 Workspace의 `tests`, 명세·티켓·조사·시제품·신규 용어집/ADR 등 작업 문서는 `artifacts`, 실행 결과·cache는 `results`에 둔다. 기존 제품 테스트와 문서는 자동 이동하지 않는다. Skill의 상대 산출물 경로 예시는 이 저장 규칙으로 해석하고 프로젝트 Harness에는 실제 경로를 연결한다.
- 이미 합의한 요구사항·검사 경계는 재사용한다. 코드나 문서에서 확인할 사실은 먼저 조사한다. 임시 파일 생성을 새 설계 승인으로 확대하지 않는다.
- 신규 기능·화면 또는 동작·데이터·권한의 주요 변경은 설치된 `design/references/design-package.md`를 읽고 필요한 화면·처리·DB·검증 설계를 묶어 제시한 뒤 실제 사용자 승인 후 구현한다. 세션 길이나 `implement`·`tdd` 직접 호출로 이 단계를 생략하지 않는다. 기존 승인 설계는 재사용하고 단순 오타·기존 계약을 복구하는 국소 수정은 간단한 설명과 검증으로 진행한다.
- 설계·UI 검증은 `design/references/tool-routing.md`에 따라 기존 화면·컴포넌트를 기준으로 필요한 기능과 사용 가능한 도구를 선택한다. Figma 또는 로컬 시안으로 검토하며 계정·플러그인 설치를 선행 조건으로 삼지 않는다. 지정 테스트 URL은 재사용하고 환경 선택이 불명확할 때만 질문한다. 실제 변경 반영을 확인한 브라우저 화면을 승인 시안·기존 패턴과 비교하고, 도구의 기여·대체 사유·미검증 범위를 짧게 보고한다.
- 요구사항 답변은 아직 제시하지 않은 설계의 승인이 아니다. 제시된 설계의 승인 후에는 구현·티켓 분할·검사마다 재승인을 요구하지 않는다. 합의 결과를 실질적으로 바꾸는 부분만 다시 검토하며 새 사본·해시·승인 원장을 만들지 않는다.
- 구현 요청만으로 commit/push, 외부 이슈·PR 게시, 운영 배포·데이터 변경·외부 발송 권한을 확대하지 않는다. 세션에서 이미 받은 해당 권한은 유지한다. 권한이 없으면 로컬 변경·초안을 완성하고 실제 외부 작업 직전에만 필요한 결정을 묻는다.
- 현재 작업 리뷰에는 관련 staged·unstaged·untracked 변경을 포함한다. 사용자의 기존 변경을 보존한다. 실행하지 않은 검사·외부 연결을 성공했다고 보고하지 않는다.
- 기본 외부 도구는 START-HERE-CODEX.md의 별도 설치 단계에서 구성한다. 스킬 설치는 MCP 설정·인증을 변경하지 않는다. 기존 외부 연결을 재사용하고 계정별 인증을 구분한다.
